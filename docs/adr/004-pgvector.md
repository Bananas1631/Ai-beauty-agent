# ADR 004. Векторы — в PostgreSQL (pgvector), а не в отдельной векторной БД

- Статус: принято
- Дата: 2026-10-31

## Контекст

Агенту нужен поиск по базе знаний салона: страницы сайта, FAQ, карточка филиала.
Объём на салон — десятки страниц, сотни фрагментов; на 50 салонов — десятки тысяч векторов.
Каждый запрос фильтруется по салону: знания одного салона не должны попасть в ответ другого.

## Варианты

1. **pgvector в нашем PostgreSQL.** Векторы рядом с данными; фильтр `salon_id` и полнотекстовый
   поиск в том же SQL-запросе; одна транзакция, один бэкап, одна точка отказа.
2. **Qdrant / Milvus / Weaviate.** Быстрее на миллионах векторов, богаче фильтрация.
   Ещё один сервис: память, мониторинг, бэкап, синхронизация удалений с PostgreSQL.
3. **Облачная векторная БД.** Нет администрирования, но тексты салонов и клиентов уходят
   к внешнему провайдеру, часто за рубеж (152-ФЗ), и счёт растёт с числом запросов.

## Решение

pgvector: образ `pgvector/pgvector:pg17` уже используется, расширение включено первой миграцией.
Индекс HNSW по косинусному расстоянию, гибридный поиск с полнотекстовым (RRF) — блок 5.

## Последствия

- Изоляция салонов — тем же `salon_id`, что и везде; отдельной синхронизации нет.
- Пересмотреть, если векторов станет больше ~5 млн или p95 поиска превысит 100 мс:
  тогда вынести поиск в Qdrant, оставив PostgreSQL источником правды.
