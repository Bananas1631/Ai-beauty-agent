# ADR 008. Мультитенантность: много салонов в одной системе

- Статус: принято
- Дата: 2026-11-14

## Контекст

Один экземпляр сервиса обслуживает много салонов. Данные салонов — клиенты с телефонами,
переписка, записи — персональные данные по 152-ФЗ: утечка между салонами недопустима ни через
API, ни через ответ агента, ни через поиск по базе знаний. Салонов в первый год — десятки,
не тысячи; администрирует систему один человек.

## Варианты

1. **База данных на салон.** Сильная изоляция, но миграции, бэкапы и пулы соединений умножаются
   на число салонов; для соло-фаундера это неподъёмная эксплуатация.
2. **Схема PostgreSQL на салон.** Те же миграции N раз, `search_path` в каждом соединении,
   сложные общие запросы для биллинга и аналитики.
3. **Общие таблицы с `salon_id` в каждой строке.** Одна схема и одна миграция; изоляция
   обеспечивается кодом и ограничениями БД.
4. **Общие таблицы + Row-Level Security в PostgreSQL.** Изоляция на уровне СУБД, но нужна
   установка `app.salon_id` в каждой транзакции и отдельная роль для фоновых задач,
   которые работают со всеми салонами.

## Решение

Вариант 3, с возможностью добавить RLS (вариант 4) поверх, не меняя схему.

- Каждая таблица с данными салона наследует `SalonOwned`: колонка `salon_id` с внешним ключом
  на `salons` (`ON DELETE RESTRICT`) и индексом.
- Уникальность — в пределах салона: `UNIQUE (salon_id, phone)` у клиентов,
  `UNIQUE (salon_id, external_id)` у услуг и мастеров, `UNIQUE (salon_id, idempotency_key)`
  у записей, `UNIQUE (salon_id, dedupe_key)` у исходящих сообщений.
- Доступ к данным — только через репозитории-наследники `SalonRepository`: `salon_id` передаётся
  в конструктор и подставляется в каждый запрос (`_select()`) и в каждую новую строку (`add()`).
  Код выше репозитория не пишет `where(salon_id == ...)` руками и поэтому не может его забыть;
  `get(id)` строки чужого салона возвращает `None`, даже если id верный.
- Салон определяется не из данных клиента, а из точки входа: адрес страницы `/s/{slug}`,
  аккаунт канала в URL вебхука (`/webhooks/telegram/{account_id}`) с проверкой секрета этого
  аккаунта, JWT администратора с `salon_id` внутри. Один бот или сообщество VK можно подключить
  только к одному салону.
- Агент получает инструменты, уже привязанные к салону диалога; ID салона нет в аргументах
  инструментов, и модель не может попросить данные другого салона. Гибридный поиск по базе знаний
  фильтрует фрагменты по `salon_id` в SQL до ранжирования.
- Ключи Redis содержат ID салона или аккаунта канала, кэш одного салона не отдаётся другому.

## Последствия

- Одна миграция, один бэкап, один пул соединений; аналитика и биллинг по всем салонам — обычный SQL.
- Тесты изоляции: фикстуры `salon` и `other_salon`, проверки, что репозитории, поиск по базе
  знаний и подключение каналов не дают увидеть или занять данные другого салона
  (`tests/integration/db/test_tenant_isolation.py`, `tests/integration/rag`, `tests/integration/channels`).
- Ошибка в обход репозитория (сырой SQL без `salon_id`) не ловится СУБД. Снижаем риск ревью и
  тестами; чистый SQL аналитики (блок 7) получает `salon_id` именованным параметром.
- Пересмотреть и включить RLS, если появятся сотрудники с доступом к БД, внешние разработчики
  или салон потребует договорной изоляции; при сотнях салонов — шардирование по `salon_id`.
