# ADR 014. Индексатор сайтов — отдельный сервис; остальное — модульный монолит

- Статус: принято, переход по strangler fig идёт (`KNOWLEDGE_BACKEND`: local → shadow → indexer)
- Дата: 2026-12-26
- Код: `services/indexer/` (сервис), `adapters/knowledge_client.py`, `rag/remote.py`,
  `events/handlers/knowledge.py`, события `site.reindex.requested` и `knowledge.updated`;
  контракт — `tests/contract/test_indexer_api.py`

## Контекст

С ADR 001 проект — модульный монолит: один образ, одна база, процессы api, worker, beat, relay и
consumers. Это дёшево в эксплуатации для одного разработчика. Но одна часть живёт по другим законам —
индексация сайтов салонов:

| | Диалог с клиентом | Индексация сайта |
| --- | --- | --- |
| Частота | постоянно, секунды на ответ | раз в недели, по кнопке или онбордингу |
| Длительность | 2–8 с | минуты (30 страниц с паузами, медленные сайты) |
| Ресурсы | ждёт LLM и CRM | ходит в чужой интернет, парсит HTML, считает эмбеддинги |
| Риски | — | SSRF, «тяжёлые» страницы, зависшие сайты |
| Нужна для ответа клиенту | да | нет: агент читает уже готовый индекс |

Обход сайта в общем воркере Celery занимал процесс на минуты, а сбой парсера на странице салона
падал в том же процессе, что отвечает клиентам. Сайт приходит из CRM или от оператора — это
недоверенный вход, и изолировать работу с ним выгодно и с точки зрения безопасности.

## Решение

Вынести **только** индексацию сайтов в сервис `services/indexer`:

- **Своя схема `knowledge`** в том же PostgreSQL (`documents`, `chunks`, очередь обходов, outbox,
  обработанные события), свои миграции Alembic с таблицей версий `knowledge.alembic_version`, своя
  роль БД в проде с правами только на эту схему. Внешних ключей на таблицы основного сервиса нет:
  `salon_id` — просто идентификатор из события.
- **Свой образ и деплой** (`services/indexer/Dockerfile`, свои сервисы в compose и чарте): API
  (`uvicorn beauty_indexer.api:create_app`) и воркер (`python -m beauty_indexer.worker`).
- **Асинхронно — события.** Основной сервис публикует `site.reindex.requested` через свой outbox;
  индексатор в группе `indexer` превращает его в строку `reindex_jobs` (миллисекунды — потребитель
  не держит партицию минутами), исполнитель обходит сайт и в одной транзакции завершает задачу и
  пишет `knowledge.updated` в свой outbox. Основной сервис (группа `knowledge-sync`) кладёт новую
  версию в Redis — ключ кэша ответов (ADR 011) меняется — и закрывает задачу в JobStore, которую
  видит администратор.
- **Синхронно — REST.** Поиск фрагментов для агента — `POST /v1/salons/{id}/search` с таймаутом 2 с,
  одним повтором для чтения и circuit breaker, как к YCLIENTS. Индексатор недоступен — агент
  получает пустой ответ по сайту и говорит «уточню у администратора»; FAQ и карточка филиала
  по-прежнему ищутся в основном сервисе.
- **OAuth2.** Основной сервис выпускает себе токен со scope `knowledge:read` (Ed25519, 15 минут);
  индексатор проверяет его по JWKS основного сервиса без сетевого запроса на каждый вызов.
- **Общий код — библиотека, а не копия.** Обход без SSRF, очистка HTML, нарезка, эмбеддинги и RRF —
  в `beauty_agent.rag`, индексатор импортирует их из того же репозитория и того же `poetry.lock`.
  Когда появится второй сервис, которому это нужно, библиотека станет отдельным пакетом.

### Переход по strangler fig

| Режим | Ответ агенту | Переиндексация | Что смотрим |
| --- | --- | --- | --- |
| `local` | свой модуль RAG | задача Celery | — |
| `shadow` | свой модуль; индексатор спрашивается в фоне тем же вопросом | Celery (ведёт задачу) + событие индексатору | `beauty_agent_knowledge_shadow_total{result}` и лог `knowledge_shadow_compare`: совпадение страниц топ-3 |
| `indexer` | сайт — индексатор, FAQ и карточка — свой модуль (RRF) | только событие индексатору | ошибки и p95 индексатора, `knowledge_updated` |

Переключение `shadow → indexer` — когда за неделю на пилотах не меньше 95% сравнений `same` или
`partial` и нет `error` дольше минуты. После недели в `indexer` удаляется старый код обхода в
основном сервисе (`workers/indexing.py`, страницы сайта в `knowledge_chunks`) — миграцией в два
релиза (expand/contract, `scripts/check_migrations.py`). На 26 декабря реальные пилоты ещё в
`local`: сравнение и удаление — после включения `shadow` на сервере.

## Почему только индексатор

Критерии выделения сервиса: другой профиль нагрузки, независимость от критического пути ответа,
отдельная зона риска, понятный узкий контракт. Индексация проходит все четыре. Остальное — нет:

- **Агент, движок записи, диалог** — один критический путь с общими транзакциями (запись, outbox,
  согласия). Разрезать его — значит получить распределённые транзакции и саги там, где сейчас
  одна транзакция PostgreSQL.
- **Мессенджеры и вебхуки** — тонкий слой над тем же диалогом.
- **Аналитика** уже отделена событиями (Kafka → ClickHouse, шаг 24) без отдельного сервиса.

## Чем платим

- **Сеть.** Поиск — HTTP-вызов вместо SQL в той же транзакции: +1–3 мс внутри сети Docker,
  плюс отказ индексатора как новый вид сбоя (закрыт таймаутом, breaker и ответом «уточню»).
- **Согласованность.** Новая версия базы знаний видна агенту после `knowledge.updated` — секунды
  после окончания обхода, а не сразу (eventual consistency). Для сайта салона это неважно.
- **Второй деплой и второй набор миграций**, свой образ в CI и чарте, ещё два процесса в compose.
- **Контракт.** Формат ответа — договорённость двух деплоев; её проверяет контрактный тест:
  индексатор может добавлять поля, но не удалять и не переименовывать обязательные для клиента.

## Это ещё микросервис или уже распределённый монолит?

Признаки распределённого монолита — общая схема, синхронные цепочки вызовов, совместные релизы.
Здесь: схема своя (общий только экземпляр PostgreSQL — ради одного бэкапа на одном сервере);
запись — только событиями, синхронно — один вызов чтения с деградацией; релизы независимы, пока
соблюдается контракт. Отдельный экземпляр БД — шаг, когда индексатору понадобится другое железо
(например, GPU для эмбеддингов).

## Как проверяли

- `services/indexer/beauty_indexer/tests/`: событие → задача (повтор события не создаёт вторую),
  обход сайта → `knowledge.updated` с версией и job_id, неизменённый сайт не переиндексируется и
  версия не меняется, недопустимый адрес → `failed` с причиной, брошенная задача берётся снова,
  а салон, который уже обходят, пропускается; поиск по точному слову, изоляция салонов, токен
  чужого сервиса и чужого партнёра отвергается, токен после ротации ключа принимается; миграции
  совпадают с моделями и откатываются.
- Основной сервис: клиент (повтор, breaker, новый токен после 401, ответ не по контракту),
  смешивание сайта и FAQ, теневое сравнение, версия для кэша, обработчик `knowledge.updated`,
  контрактный тест.
