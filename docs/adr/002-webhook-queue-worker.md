# ADR 002. Вебхук → очередь → воркер

- Статус: принято
- Дата: 2026-11-09

## Контекст

Мессенджеры (Telegram, VK, позже MAX) присылают сообщения клиентов вебхуками. Ответ агента
занимает от 2 до 20 секунд: несколько вызовов LLM и запросы к YCLIENTS. Мессенджеры ждут ответа
на вебхук недолго: Telegram повторяет запрос, если не получил ответ вовремя, VK после нескольких
неудач отключает сервер Callback API. Клиенты пишут пачками («Здравствуйте» / «хочу на маникюр» /
«в пятницу»), и на каждое сообщение отдельный ответ агента выглядит странно и стоит втрое дороже.

## Варианты

1. **Отвечать прямо в HTTP-запросе вебхука.** Просто, но запрос висит секунды, мессенджер
   повторяет его, и клиент получает два ответа; падение процесса посреди ответа теряет сообщение;
   склеить пачку сообщений нельзя.
2. **Фоновая задача FastAPI (`BackgroundTasks`).** Вебхук отвечает быстро, но задача живёт в памяти
   процесса api: перезапуск при деплое или падение теряют её, повторов и учёта упавших задач нет.
3. **Вебхук → очередь → воркер.** Вебхук только проверяет подпись, отсекает повтор и ставит
   сообщение в очередь; отвечает агент в отдельном процессе.

## Решение

Вариант 3. Путь сообщения:

1. `api/v1/webhooks.py` сверяет секрет вебхука (`X-Telegram-Bot-Api-Secret-Token`, поле `secret`
   у VK) через `hmac.compare_digest` **до** запроса в БД, ограничивает тело 256 КБ.
2. `InboundGate.accept` отсекает повтор по ID обновления (`SET NX` в Redis на 24 часа), кладёт
   сообщение в список склейки (`conversation/debounce.py`) и ставит задачу с задержкой 2,5 секунды.
   Вебхук отвечает 200 — обычно за единицы миллисекунд.
3. Воркер Celery (`workers/messages.py`) забирает накопленную пачку. Если за время задержки пришли
   новые сообщения, пачку забирает более поздняя задача — агент вызывается один раз на всю пачку.
4. Сервис диалога сохраняет ответ агента и строку в таблице исходящих (outbox) в одной транзакции,
   затем `Outbox.deliver` отправляет её и ставит отметку «отправлено».

Доставка задач идёт по принципу «хотя бы один раз», поэтому идемпотентен каждый шаг: повтор
вебхука отсекает Redis, повтор задачи получает ту же пачку (её ключ — токен задачи), повтор ответа
видит отметку `SENT` в outbox и не отправляет текст второй раз.

## Последствия

- Мессенджер получает 200 сразу и не повторяет запрос; агент может думать сколько нужно.
- Упавшая задача повторяется с растущей паузой, после трёх попыток уходит в очередь «мёртвых»
  задач (DLX), администратор получает уведомление — сообщение клиента не теряется молча.
- Появляются брокер (RabbitMQ) и процессы воркеров — их выбор в [ADR 003](003-celery-rabbitmq.md).
- Отказ мессенджера доставить ответ (бот заблокирован клиентом) — окончательная ошибка: строка
  outbox получает статус `FAILED`, повторов нет. Временная ошибка (сеть, 5xx, лимит) — повтор задачи.
- Виджет сайта остаётся на WebSocket без очереди: клиент сам держит соединение и ждёт ответ.
