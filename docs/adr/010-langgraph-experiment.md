# ADR 010. Эксперимент: тот же агент на LangGraph

- Статус: принято — остаёмся на своём цикле (ADR 005)
- Дата: 2026-12-12
- Код эксперимента: ветка [`experiment/langgraph`](https://github.com/Bananas1631/Ai-beauty-agent/tree/experiment/langgraph),
  `src/beauty_agent/agent/langgraph_agent.py`; в `main` не вливается

## Вопрос

«Почему не LangChain/LangGraph?» В ADR 005 решение принято до того, как агент заработал. Теперь
есть evals, и его можно проверить измерением, а не мнением.

## Как сравнивали

- Тот же агент: заменена только оркестрация «модель → инструменты». Цикл стал графом `StateGraph`
  без супервизора: `model → (tools → model)* → END`, лимит шагов — через `recursion_limit` и условие
  на ребре. Граф компилируется один раз на процесс, агент и контекст передаются через `config` —
  лучший для LangGraph случай.
- Общие части не менялись: входные и выходные guardrails, промпт и контекст, проверка аргументов
  Pydantic с одной попыткой исправиться, передача администратору, трассы.
- Модель — наш `LLMClient`, а не чат-модели LangChain: офлайн-модели для evals там нет, а Qwen
  (Cloud.ru), GigaChat и YandexGPT доступны только через сторонние интеграции. Иначе сравнивались бы
  адаптеры, а не цикл.
- Evals: 100 сценариев записи `booking/v2` и 30 провокаций `attacks/v1`, офлайн-модель, по 3 прогона
  каждого варианта (`python -m evals.run --engine own|langgraph`).

## Результаты

| Метрика | Свой цикл | LangGraph |
| --- | --- | --- |
| Успешные сценарии | 95,4% | 95,4% |
| Точность записи | 92,5% | 92,5% |
| Передача администратору | 100% | 100% |
| Инварианты (запись только на предложенное время, цены из каталога, провокации) | 100% | 100% |
| Стоимость диалога | одинаковая: те же промпты и вызовы модели | |
| Время агента на сообщение без модели, p50 / p95 | 2 / 4 мс | 25 / 50 мс |
| Прогон 130 сценариев | 4,3 с | 7,0 с |
| Новых зависимостей | 0 | 16 пакетов (langchain-core, langsmith, langgraph-checkpoint, orjson, zstandard…) |
| Импорт | — | +1,9 с к старту процесса |
| Код оркестрации | ~30 строк цикла | ~100 строк графа + состояние и конфигурация |

## Вывод

1. **Точность и стоимость не зависят от оркестрации.** Их определяют модель, промпт, инструменты
   и guardrails — всё это у нас своё и общее для обоих вариантов. Фреймворк ничего не добавил
   и ничего не сломал.
2. **Накладные расходы LangGraph — около 22 мс на сообщение.** На фоне 1,5–3 секунд ожидания модели
   это меньше 1–2% — для пользователя незаметно и само по себе не причина отказаться.
3. **Решает цена владения:**
   - 16 пакетов в образе, включая `langsmith` — SDK облачной телеметрии: одна переменная окружения
     `LANGCHAIN_TRACING_V2=true` отправит переписку клиентов за рубеж, что недопустимо по 152-ФЗ;
   - лишний слой при отладке: ошибка в узле графа приходит из машинерии Pregel, а не из нашего цикла;
   - частые несовместимые изменения API у langchain-core и langgraph — регулярная плата за обновления;
   - то, ради чего LangGraph берут, нам не нужно: сценарий один, агентов один, долгие процессы
     с ожиданием событий запланированы на Temporal (блок 11), где у них есть ретраи и история.
4. **Остаёмся на своём цикле.** Пересмотреть, если появятся несколько агентов с передачей задач
   между ними, ветвящиеся сценарии на десятки состояний или понадобится визуальная отладка графа —
   тогда граф окупит свой вес. Эксперимент в ветке показывает, что перенос занимает день: логика
   агента от оркестрации отделена.

## Ответ на собеседовании в двух фразах

Мы собрали того же агента на LangGraph и прогнали на тех же 130 сценариях: точность и стоимость
совпали до процента, LangGraph добавил 22 мс на сообщение, 16 зависимостей и риск отправить
персональные данные в LangSmith. Для одного агента с одним сценарием свой цикл на 30 строк проще
поддерживать; граф окупится, когда агентов станет несколько.
