# ADR 003. Очередь задач на Celery и RabbitMQ

- Статус: принято
- Дата: 2026-11-09

## Контекст

По [ADR 002](002-webhook-queue-worker.md) сообщения клиентов обрабатываются в фоне. Нужны:
отложенный запуск (склейка сообщений, позже напоминания за 24 и 2 часа), повторы с растущей
паузой, очередь «мёртвых» задач, периодические задачи (ночная синхронизация каталога, удаление
старых диалогов, еженедельный отчёт) и несколько процессов воркеров. Код проекта асинхронный.

## Варианты

1. **Celery + RabbitMQ.** Стандарт в Python-вакансиях; есть повторы, маршрутизация по очередям,
   расписание (beat), подтверждение после выполнения. RabbitMQ даёт DLX «из коробки». Минус:
   Celery синхронный, async-код нужно запускать аккуратно.
2. **Celery + Redis как брокер.** Redis уже есть, но нет настоящего DLX, а задачи с задержкой
   (`countdown`) после падения воркера возвращаются в очередь только через `visibility_timeout`.
3. **arq / taskiq / dramatiq.** arq и taskiq нативно асинхронные, но меньше распространены,
   беднее инструменты эксплуатации; переход на них не даёт ничего, что нужно продукту сейчас.
4. **Kafka.** Журнал событий, а не очередь задач: нет отложенных задач и повторов по одной задаче.
   Kafka появится в блоке 9 для событий аналитики, а не для обработки сообщений.

## Решение

Celery 5 + RabbitMQ 4 (`workers/celery_app.py`):

- `task_acks_late`, `task_reject_on_worker_lost`, `worker_prefetch_multiplier=1` — сообщение
  подтверждается после выполнения, падение воркера его не теряет.
- `task_acks_on_failure_or_timeout=False` и аргументы `x-dead-letter-exchange` у очередей:
  задача после последней попытки отклоняется и по DLX попадает в очередь `dead`.
- Только JSON (`accept_content=["json"]`): из очереди не выполнится произвольный pickle.
- Очереди `messages` (сообщения клиентов) и `periodic` (фоновые задачи) раздельно: тяжёлая ночная
  задача не задерживает ответы клиентам.

Три ловушки async-кода и как они обойдены:

1. **Публикация задачи из async-эндпоинта блокирует цикл событий** (`apply_async` — синхронный
   сетевой вызов). `CeleryQueue.schedule` выполняет его в пуле потоков (`asyncio.to_thread`).
2. **Движок SQLAlchemy с asyncpg привязан к циклу событий** и ломается при переиспользовании между
   разными `asyncio.run`. У каждого процесса воркера свой постоянный цикл событий и свой `Runtime`
   (движок БД, Redis, HTTP), создаются в `worker_process_init` и закрываются при остановке.
3. **Лимит YCLIENTS 5 запросов в секунду должен быть общим** для всех процессов. Ограничитель
   переехал в Redis (`RedisTokenBucket`, Lua-скрипт со временем сервера Redis).

Две особенности RabbitMQ 4, найденные интеграционным тестом на настоящем брокере:

- RabbitMQ 4 запрещает временные неэксклюзивные очереди, а их создают удалённое управление
  воркерами (pidbox) и события задач. Без `worker_enable_remote_control=False` и
  `worker_send_task_events=False` воркер бесконечно переподключается. Цена — не работают
  `celery inspect` и Flower; состояние смотрим в логах, метриках и панели RabbitMQ.
- Воркер объявляет только очереди, которые читает (`-Q messages,periodic`). Если обменник `dlx`
  не объявлен, RabbitMQ молча выбрасывает «мёртвое» сообщение. `declare_queues` объявляет все
  очереди при старте воркера (сигнал `worker_init`).

## Последствия

- В docker-compose появились сервисы `worker` и `beat` из того же образа, что и api.
- На Windows для локального запуска нужен `--pool=solo` (`make worker`), в контейнерах — prefork.
- `tests/integration/workers/test_celery_dlx.py` на RabbitMQ в testcontainers проверяет, что задача
  после всех повторов оказывается в очереди `dead`.
- Пересмотреть, если понадобятся долгие процессы с ожиданием событий и компенсациями —
  это Temporal (блок 11), а не очередь задач.
