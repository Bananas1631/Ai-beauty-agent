# ADR 013. Задачи — Celery и RabbitMQ, события — Kafka

- Статус: принято
- Дата: 2026-12-24
- Код: `domain/events.py`, `events/` (outbox, producer, relay, consumer, handlers), миграции 0010–0011;
  каталог событий — `docs/events.md`

## Контекст

С шага 15 вся фоновая работа идёт через Celery и RabbitMQ (ADR 003): ответить клиенту, напомнить
о записи, синхронизировать каталог. Это **задачи** — «сделай это»: у каждой один исполнитель,
выполненная задача из очереди исчезает.

Появились **факты**, которые нужны многим: запись создана, перенесена, засчитана ИИ; клиент написал;
агент ответил и потратил столько-то. Их читают еженедельный отчёт, аналитика (ClickHouse, шаг 24),
сервис биллинга на Kotlin (шаг 29) — и каждому нужен весь поток, а не своя доля. Добавить
нового читателя «задним числом» RabbitMQ не даёт: сообщение, которое уже прочитано, ушло.

## Решение

- **Задачи остаются в Celery и RabbitMQ.** Повторы с паузой, DLX, приоритеты очередей, расписание
  beat — всё это уже работает и нужно именно задачам.
- **События — в Kafka.** Журнал хранится 7 дней; каждая группа потребителей читает его независимо
  и со своей позиции; новую группу можно запустить с начала топика (перечитывание).
- **Transactional outbox.** Событие пишется в `event_outbox` в той же транзакции, что и данные;
  relay публикует его идемпотентным продюсером (acks=all) и отмечает. Без outbox запись в БД и
  событие в Kafka могли бы разойтись. Гарантия — at-least-once: дубль возможен, потеря — нет.
- **Порядок внутри салона.** Ключ сообщения — salon_id (одна партиция на салон); relay берёт
  салон под транзакционную advisory-блокировку, строки — `FOR UPDATE SKIP LOCKED` по порядку id.
  Одного SKIP LOCKED мало: второй relay взял бы более поздние события того же салона и опубликовал
  бы их раньше. Проверено интеграционным тестом с двумя relay на настоящей Kafka.
- **Идемпотентные потребители.** `processed_events (group, event_id)` пишется в одной транзакции
  с результатом; commit offset — после обработки. Три неудачи — событие в `<топик>.dlq` с причиной
  в заголовках и уведомление администратору; партиция не встаёт из-за одного события.
- **Без персональных данных в событиях.** Только ID, время, суммы и перечисления: журнал читают
  разные группы и он живёт неделю отдельно от сроков хранения переписки.
- **Топики по сущности**: `beauty.bookings`, `beauty.messages`, `beauty.llm` — 6 партиций, 7 дней.
  Автосоздание топиков в брокере выключено: опечатка не создаст топик с настройками по умолчанию.

Первый потребитель — недельная статистика салона (`weekly-stats`): отчёт по понедельникам больше
не делает SQL-запросы по сообщениям и черновикам всех салонов. Переключение — `KAFKA_ENABLED`,
до развёртывания Kafka отчёт строится по-старому.

## Когда хватило бы Redis Streams

Redis Streams тоже дают группы потребителей, подтверждения и перечитывание, а Redis уже есть.
Для одного-двух потребителей и событий, которые не нужно хранить дольше памяти Redis, этого
достаточно — тот же потребитель на Streams сделан в ветке эксперимента `experiment/redis-streams`.
Kafka выбрана, потому что:

- хранение на диске неделями с предсказуемой ценой, а не в памяти Redis рядом с кэшем и сессиями;
- партиции с ключом дают порядок внутри салона и масштабирование потребителей «из коробки»;
- перечитывание с произвольного времени (`offsets_for_times`) — для ClickHouse и новых сервисов;
- готовые клиенты и Schema-подход для сервиса на Kotlin (шаг 29) и Kafka UI для отладки.

Цена — ещё один сервис в эксплуатации (JVM, ~512 МБ памяти) и relay. Для одного сервера это
заметно, поэтому Kafka — один узел KRaft без ZooKeeper, а источник правды — PostgreSQL:
бэкап Kafka не нужен, потерянное публикуется заново из outbox.

## Почему не так

- **Публиковать в Kafka прямо из кода, без outbox.** Падение между commit и send (или наоборот)
  даёт расхождение, которое потом не найти.
- **Debezium (CDC) вместо relay.** Ещё один кластерный сервис (Kafka Connect) и события в форме
  строк таблиц, а не доменных фактов; для одного сервера и одной БД — избыточно.
- **Всё в Kafka, включая задачи.** Повторы с задержкой, DLX и расписание пришлось бы писать заново;
  задачи с одним исполнителем — работа очереди, а не журнала.

## Последствия

- Новые сервисы: `kafka` (KRaft), `relay`, `consumers`, Kafka UI по профилю `events`.
- Метрики: очередь outbox, lag групп, события в DLQ; алерт, если lag растёт 10 минут подряд.
- Новый потребитель — новый обработчик в `events/handlers/` и строка в `events/consumers.py`;
  продюсеры о нём не знают.
