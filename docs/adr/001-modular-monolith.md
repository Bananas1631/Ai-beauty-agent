# ADR 001. Модульный монолит вместо микросервисов

- Статус: принято
- Дата: 2026-11-07 (перенесено с 24 октября)

## Контекст

Один разработчик, пилоты в нескольких салонах, нагрузка — десятки сообщений в минуту в пике.
Нужно быстро менять агента, движок записи и каналы, не теряя надёжности записи.

## Варианты

1. **Микросервисы** (агент, запись, каналы, RAG отдельно): независимый деплой и масштабирование,
   но сетевые вызовы между частями, распределённые транзакции вокруг записи, несколько CI и мониторингов.
2. **Модульный монолит**: один сервис и один образ, модули с явными границами (`adapters`, `domain`,
   `agent`, `rag`, `conversation`, `api`), общий PostgreSQL. Модули общаются через интерфейсы
   (`BookingProvider`, `LLMClient`, `Catalog`, `SalonInfoSource`), а не через таблицы друг друга.

## Решение

Модульный монолит. Запись клиента — одна транзакция в одной базе, без саги. Тесты поднимают всё
приложение целиком. Фоновые задачи (блок 6) — воркеры Celery из того же образа.

## Последствия

- Границы модулей держатся интерфейсами и импортами: домен не импортирует API и адаптеры.
- Масштабирование — больше процессов того же образа за балансировщиком (состояние в Redis и PostgreSQL).
- Выделять сервис стоит, когда у части появятся своя команда, свой ритм релизов или своя нагрузка:
  первым кандидатом станет биллинг (блок 11, сервис на Kotlin) — у него другой язык и другие требования к деньгам.
