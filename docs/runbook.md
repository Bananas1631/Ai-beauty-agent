# Runbook: что делать при авариях

Сервер: `/opt/beauty-agent`, все команды — `docker compose -f docker-compose.prod.yml …` (ниже — `dc`).
Алерты приходят в Telegram из Grafana; дашборд — `ssh -L 3000:127.0.0.1:3000 <сервер>`, http://localhost:3000.
Первым делом — `dc ps` и `curl -s localhost:8000/ready` изнутри сервера: `/ready` показывает, какая
зависимость не отвечает. По `trace_id` из жалобы или Sentry ищется вся история запроса:
`dc logs api worker --since 1h | grep <trace_id>`.

## YCLIENTS недоступен

**Признаки:** алерт «Растут ошибки внешних систем» с `provider="yclients"`; администраторам приходят
«CRM недоступна, подтвердите запись вручную».

**Что уже делает система:** чтение повторяется 3 раза с паузой; после серии ошибок circuit breaker
перестаёт дёргать YCLIENTS на 30 секунд; запись не теряется — сохраняется со статусом «ждёт
подтверждения», администратор получает уведомление; отмена и перенос уходят администратору.
Клиенту агент честно говорит, что администратор подтвердит запись.

**Что делать:**
1. Проверить статус YCLIENTS (status.yclients.com, чат партнёров) — если сбой у них, ждать.
2. `kind="auth"` — отозван или истёк токен: новый партнёрский или user-токен в `.env`, `dc up -d api worker`.
3. `kind="rate_limited"` — превышен лимит 5 запросов в секунду: проверить, не идёт ли ночная
   синхронизация каталога днём (`periodic.catalog_sync`), лимит общий для всех процессов (Redis).
4. После восстановления — пройтись по записям «ждёт подтверждения» (уведомления в админ-боте).

## LLM недоступна или отвечает ошибками

**Признаки:** ошибки `provider="llm:<модель>"`, в логах `llm_fallback`.

**Что уже делает система:** роутер переходит на следующую модель из списка салона
(Qwen → GigaChat → YandexGPT); если не ответила ни одна — диалог передаётся администратору,
клиент получает «Передаю ваш вопрос администратору».

**Что делать:**
1. Посмотреть, какая модель падает (дашборд «Ошибки внешних систем»), проверить статус провайдера.
2. Если провайдер лежит долго — убрать модель из `LLM_DEFAULT_MODELS` (или из `llm_models` салона),
   `dc up -d api worker`: ответы не будут ждать таймаута недоступной модели.
3. Ошибка 401/403 — ключ отозван или кончились деньги на счёте провайдера: пополнить или заменить ключ.

## Очередь не разбирается

**Признаки:** алерт «Очередь сообщений не разбирается» (в `messages` больше 50 сообщений 10 минут
или RabbitMQ недоступен — длина `-1`); клиенты в мессенджерах не получают ответов, веб-чат работает.

**Что делать:**
1. `dc ps worker rabbitmq` — живы ли контейнеры. Перезапуск: `dc restart worker`.
2. RabbitMQ не стартует — `dc logs rabbitmq --tail 100`; частая причина — кончилось место на диске
   (`df -h`): RabbitMQ при нехватке места блокирует публикацию.
3. Воркер жив, но не успевает — `dc logs worker | grep message_retry`: если повторы из-за LLM или
   YCLIENTS — см. разделы выше; если просто много сообщений — добавить процессов
   (`--concurrency` в compose) с учётом пула соединений (docs/performance.md, «Размер пула»).
4. Вебхуки при этом продолжают приниматься и отвечать 200: сообщения копятся в очереди и будут
   обработаны после восстановления, мессенджеры повторно не шлют.

## Сообщения в очереди «мёртвых» задач

**Признаки:** алерт «Сообщения клиентов в очереди мёртвых задач»; администратор салона получил
уведомление «Сообщение клиента не обработано после повторов».

**Что делать:**
1. Найти причину по логам: `dc logs worker | grep message_dead_lettered` → `trace_id` → полная история.
2. Устранить причину, затем вернуть задачи в очередь `messages` через панель RabbitMQ
   (Shovel / «Move messages» из `dead` в `messages`) или удалить, если клиенту уже ответил администратор.
   Повторная обработка безопасна: повтор не даст второго ответа (outbox).

## База данных недоступна

**Признаки:** `/ready` → `postgres: error`, 5xx в API, алерт «API отвечает ошибками 5xx».

**Что делать:**
1. `dc ps postgres`, `dc logs postgres --tail 100`. Кончилось место — `df -h`, почистить старые
   образы `docker image prune`, логи ротируются автоматически.
2. «too many connections» — проверить, не запущено ли лишних процессов; пул на процесс задан
   `POSTGRES_POOL_SIZE` и `POSTGRES_MAX_OVERFLOW`.
3. Повреждение данных — восстановление из бэкапа (`backup.sh`, проверка восстановления — в deploy/README.md):
   сначала на отдельную базу, проверить, затем переключить.

## Redis недоступен

**Признаки:** `/ready` → `redis: error`.

**Последствия:** не работают склейка сообщений, блокировки диалогов, лимиты частоты и кэш слотов —
API отвечает ошибками. Данные не теряются: состояние диалогов восстанавливается из PostgreSQL.

**Что делать:** `dc restart redis`; если не помогает — `dc logs redis`, проверить место и память.

## Telegram или MAX не доставляют ответы

**Признаки:** ошибки `provider="telegram"` / `"max"` с `kind="rejected"`.

**Что делать:**
1. `rejected` по одному чату — клиент заблокировал бота, это нормально (строка outbox `failed`).
2. `rejected` по всем чатам салона — отозван токен бота: новый токен через `scripts/onboard_salon.py`.
3. `unavailable` — сбой мессенджера: исходящие досылаются автоматически (`periodic.outbox_sweep`).
4. Вебхук перестал приходить: Telegram — `getWebhookInfo` показывает `last_error_message`;
   MAX отписывает бота после 8 часов без ответа 200 — переподписать через онбординг.

## Расход LLM салона близок к лимиту

**Признаки:** алерт «Расход LLM у салона близок к дневному лимиту».

**Что делать:** посмотреть, нет ли спама в диалогах салона (много сообщений с одного IP или сессии —
лимиты частоты это ограничивают). Если нагрузка честная — поднять `daily_llm_budget_rub` в настройках
салона. При исчерпании лимита диалоги до конца дня уходят администратору, а владелец сервиса
получает одно уведомление.

## Откат версии

`APP_IMAGE=<прошлый тег> dc up -d api worker beat`. Миграции только добавляют таблицы, колонки
и индексы, поэтому прошлая версия кода работает с новой схемой — схему при откате кода не трогаем.
